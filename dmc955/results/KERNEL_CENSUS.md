# Kernel census — every launch shape, per stage

Generated by `kernel_census.py`, which takes its phase boundaries from
`stage_attrib.phase_windows` (the single shared definition), so it works on any
trace the harness produces.

```bash
python3 kernel_census.py results/trace_f16.sqlite --csv results/kernels_f16.csv --cover 92
python3 kernel_census.py <trace> --by-name          # collapse shapes, group by name
```

CSVs: `results/kernels_f{1,4,8,16}.csv` and `results/kernels_handshake13.csv`
(all rows, all stages). Columns: stage, share, cum, n, n_per_req, total_ms,
ms_per_req, p10/p50/p90_us, grid, block, regs, smem, multimodal, name.

## Why not `ncu_targets.py shapes`

That tool answers the same question but is welded to one trace — `phases()`
hardcodes `FRAME_KERNELS = 1270` and `N_FRAMES = 13`, so it silently mis-slices any
run with a different frame count. It also defaults to `--top 14`, truncating the
tail, and never reports block size.

## The grouping key

`(name, grid, block, registers, shared memory, duration cluster)`. The duration
cluster is not optional: llama.cpp launches q_proj (K=3584) and down_proj
(K=18944) at the **same** grid, registers and shared memory, differing only in the
weight streamed — 25.7 MB vs 136 MB, ~29 us vs ~144 us. nsys records no problem
size, so duration is the only trace-visible discriminator. Such rows are split and
flagged `*`.

Cross-check: on `handshake_7B` the census reproduces the 2026-09-02 survey's own
figures — `mul_mat_vec_f @18944` 49.18% (survey 49.07), `@3584` 24.75% (24.69).

## Three findings the census surfaces

### 1. The ncu survey missed 17.0% of the ViT stage

Shapes never profiled by `ncu_2026-09-02_7B-BF16/`:

| share | grid | kernel |
|---|---|---|
| 3.41% | 2368 | `rms_norm_f32` |
| 3.35% | 47360 | `cpy_scalar<f32→f16>` |
| 3.12% | 33152 | `k_bin_bcast` — *same name* as a profiled shape, different grid |
| 2.92% | 31635 | `convert_unary<bf16,float>` — same name, different grid |
| 1.81% | 24576 | `flash_attn_stream_k_fixup<80>` |
| 1.64% | 31635 | `convert_unary<float,bf16>` — same name, different grid |

Three of the six are the *same kernel name at a different grid* than the one
profiled, which is exactly the failure the coverage audit (`PROFILING_HANDOFF.md`
§6a) found in the reported numbers. The generated `ncu_targets.sh` did include
`rms_norm_f32`; the hand-written `run_ncu_survey.sh` dropped it.

### 2. Prefill's kernel mix is the only one that is context-dependent

Distinct launch shapes per stage:

| frames | ViT | prefill | decode |
|---|---|---|---|
| 1 | 28 | **75** | 15 |
| 4 | 30 | **95** | 15 |
| 8 | 31 | **110** | 16 |
| 16 | 27 | **131** | 15 |

ViT and decode are perfectly regular — the same ~28 and ~15 shapes regardless of
workload. **Prefill fragments**, and grows by ~3.7 shapes per frame. Two drivers:
the ubatch split produces several distinct token counts (512 / 80 / 29 / 2), and
the attention grid tracks KV depth, so each frame adds new shapes. This is the
kernel-level signature of the chunking problem in `GAP3_PREFILL.md`, and it gives
a cheap falsifiable check: **at `-ub 640` the prefill shape count should drop
sharply.** Unmeasured.

### 3. The decode attention kernel changes family with the operating point

| trace | kernel | grid | regs | smem | p50 |
|---|---|---|---|---|---|
| handshake (13 frames, fps) | `flash_attn_ext_vec<128,1>` | 756 | 166 | 8K | 27.5 us |
| trace_f16 (16 frames) | `flash_attn_ext_f16<128,128,1,8>` + stream-K fixup | 128 | 132 | 68K | 24.5 us |

Same build (`b55dcdef5`), same model — a different kernel *family*. The dispatch
is `fattn.cu:368`:

```c
const bool can_use_vector_kernel = Q->ne[0] <= 256 && Q->ne[0] % 64 == 0
                                && K->ne[1] % FATTN_KQ_STRIDE == 0;   // stride = 256
```

`K->ne[1]` is the KV length, and it is the only workload-dependent term — so
whether decode gets the batch-1-specialised vector kernel appears to hinge on the
KV length being a multiple of 256, which for a VLM is set by the visual token
count. Worth confirming directly before quoting the mechanism.

**Actionable consequence, independent of the mechanism**: the survey's
`decode__flash_attn_vec__5pct.ncu-rep` profiles a kernel that **is not used** at
the 16-frame operating point. ncu targets do not transfer across frame counts, and
any decode-attention claim must state the operating point it was measured at.
