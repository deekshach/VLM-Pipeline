# ncu survey — 2026-09-02 — Qwen2.5-VL-7B-Instruct-BF16

20 reports, 80 per-launch samples. Generated by `../run_ncu_survey.sh`.

**All previous ncu reports were deleted before this run.** They mixed two naming
schemes, several workloads, and averaged across heterogeneous kernel shapes. This
directory is the only valid ncu data.

## Workload (identical for every report)

```
Qwen2.5-VL-7B-Instruct-BF16 + mmproj-BF16
alley_1 · --base-frames 13 · -n 16 · -c 16384
--temp 0 --seed 42 -fa on --ignore-eos --no-flow-analysis --warmup-iters 0

```

13 frames = 7696 visual tokens, matching the 460-request characterization operating
point. RTX 4090, driver 580.173.02, ncu 2024.3.1.

## How targets were chosen

Not by guessing which kernel "represents" a stage. Targets were read off the nsys
`(kernel, grid)` census (`cuda_gpu_kern_gb_sum`), walking down the cumulative time
column to a coverage goal. Filenames carry the stage, the kernel, and its share.

- **ViT** uses `--kernel-id ':17:regex:NAME:'` — stream 17 is the clip backend, so
  stream filtering guarantees exclusivity. This matters for
  `ampere_bf16_s1688gemm_128x64`, which appears in BOTH stages at different grids
  (370 in ViT, 896 in prefill).
- **Prefill / decode** are separated by kernel name, verified phase-exclusive
  against the trace (`mul_mat_f<` 5211 in prefill / 0 in decode; `mul_mat_vec_f`
  the reverse; head-dim 128 vs 80 splits the two attentions).
- **Prefill attention is sampled as a CURVE** at four launch depths, because it
  drifts +229% across the phase as KV accumulates. A single sample is meaningless.

### ncu constraint discovered

`--launch-skip` cannot be combined with a stream-filtered `--kernel-id`:

```
ERROR: The option --launch-skip is not compatible with --kernel-id specified
       with context, stream, invocation filter
```

The two targets needing `-s` (`prefill__mul_mat_f`, the attention curve) therefore
use plain `-k regex:`. Safe, because both names are already phase-exclusive.

# RE-ANALYSIS 2026-09-15 — the same .ncu-rep files, the right columns

**No new data was collected.** Every number below comes from the CSVs already in
this directory. The survey's *measurements* were sound; its *column choice* hid
the answer. Regenerate with `python3 ../ncu_bottleneck.py [--rules]`.

## The column bug

Three reporting choices combined to make prefill look unexplainable:

1. **The column labelled "L2%" was `L2 Hit Rate`, not L2 throughput.** Hit rate
   says *where* traffic landed; it says nothing about whether that unit is full.
   `--set full` captured `L2 Cache Throughput` all along — never read.
2. **SOL `Memory Throughput` is max(DRAM, L2, L1)**, the dominant memory unit.
   Reading only `DRAM Throughput` reports near-nothing for any kernel whose
   working set is served from L2 — precisely the 90-97%-hit-rate GEMMs.
3. **`Compute (SM) Throughput` aggregates all pipes.** For a tensor GEMM the
   honest figure is tensor-pipe utilisation, which ncu states only in the
   `HighPipeUtilization` rule prose.

Result: for `ampere_64x128 @1184` the survey read "44.9% SM / 32.4% DRAM —
neither limit" when the same launch was at **68.8% of L2 peak**, and ncu's own
`SOLBottleneck` rule said in the file: *"Memory is more heavily utilized than
Compute: ... identify the **L2 bottleneck**."*

## The corrected result — the pipeline has TWO memory walls, not one

| population | share of stage | binding unit |
|---|---|---|
| ViT GEMMs (cutlass @1184/592, ampere @370) | 45.9% of ViT | **L2 63-73%** (DRAM 17-21, tensor 43-44) |
| ViT elementwise (silu, k_bin_bcast, 2x convert) | 25.3% of ViT | **DRAM 81-94%** |
| ViT flash-attn hd80 @384 | 15.8% of ViT | **latency-bound** — nothing >60% |
| prefill big GEMMs (@1184, @896) | 38.2% of prefill | **L2 69-74%** (DRAM 33-37, tensor 48) |
| prefill cutlass_relu @592/896 | 15.2% of prefill | **DRAM 78-83%** |
| prefill mul_mat_f @592 | 17.3% of prefill | **DRAM 94%** |
| prefill attention hd128 @256 | 7.4% of prefill | **L2, saturating to 85%** |
| prefill ampere_128x128 @112 | 5.4% of prefill | underfilled, 0.44 waves |
| decode mul_mat_vec_f | 92.8% of decode | **DRAM 94-97%** (unchanged) |
| decode flash_attn_ext_vec @756 | 4.7% of decode | **L2 78-80%**, DRAM only 50% |

Decode's DRAM wall stands exactly as published. What is new is that **ViT and
prefill are substantially an L2 wall**, which the hit-rate column made invisible.

## Corrections to specific claims in this file

- ~~"ViT — compute-bound with excellent locality"~~ **Wrong.** Those GEMMs run at
  43-44% tensor against **63-73% of L2 peak**. The 97% L2 hit rate quoted as
  evidence of good locality is what *makes* the L2 the binding unit — the traffic
  lands there instead of in DRAM. They are L2-leaning, not compute-bound.
- ~~"ViT flash_attn hd80: 48.1% SM / 94.6% L2, compute-bound"~~ ncu's own rule:
  *"low compute throughput **and** memory bandwidth ... below 60% of peak"* — it is
  latency-bound. It is also the only kernel in the survey with a healthy issue
  rate (43.3%, 0.63 eligible warps/scheduler).
- ~~"Prefill — nothing is saturated. NEEDS EXPLANATION."~~ **Answered.** See below.
- ~~Prefill attention "shifts toward compute-bound (9.5% DRAM / 53.8% SM)"~~
  **Backwards.** It shifts toward **L2 saturation**. The curve is an L2 curve:

  | skip | dur us | DRAM% | **L2%** | L2 hit | tensor% |
  |---|---|---|---|---|---|
  | 60 | 58.6 | 17.0 | 67.5 | 94.7 | 42.5 |
  | 320 | 140.6 | 13.5 | 78.2 | 97.4 | 50.9 |
  | 900 | 360.7 | 9.5 | **85.0** | 98.3 | 54.7 |

  DRAM *falling* 17 -> 9.5 was read as "becoming compute-bound". It is the growing
  KV working set being served entirely out of L2 at 98.3% hit — until the L2 runs
  out. Tensor never exceeds 54.7%.
- **s640 is still an outlier** (L2 31%, DRAM 58%, issue 6.7%) — the caution stands.

## Why prefill's GEMMs saturate nothing on the SM side

They cannot issue fast enough to saturate anything:

| | ampere_64x128 @1184 | ampere_128x64 @896 | ViT cutlass @1184 |
|---|---|---|---|
| theoretical occupancy | 16.7% | 16.7% | **8.3%** |
| warps/scheduler (hw max 12) | 2.00 | 2.00 | **1.00** |
| eligible warps/scheduler | 0.15 | 0.15 | 0.12 |
| issue slots busy | 10.2% | 10.1% | 11.6% |
| achieved vs theoretical occ | 16.0 / 16.7 | 15.7 / 16.7 | 8.3 / 8.3 |

Occupancy is **register-limited** (ncu `TheoreticalOccupancy` rule), and achieved
occupancy already equals the ceiling — so this is not an occupancy-*achievement*
problem, it is a ceiling. With 1-2 resident warps per scheduler and ~11.7-cycle
stalls on an oversubscribed tensor pipe (`CPIStall`), the scheduler issues once
every ~10 cycles. **Nothing reads high on the SM side because nothing can issue.**

This is normal for big-tile tensor GEMMs, which trade occupancy for register
tiling. It is worth recording because it means SM% will *never* look like a
bottleneck for these kernels, and reading SM% as headroom is a mistake.

## Consequence for the "complementary-bottleneck scheduling" idea

That proposal rests on "decode is 94.74% DRAM / 13.58% SM; the ViT is 41.43% SM /
**16.17% DRAM**". The 16.17% figure covers the ViT's GEMMs only and ignores the
elementwise quarter that this very survey measured at 81-94% DRAM.

Time-weighted over each stage's covered share (see `ncu_bottleneck.py`; shares
from the table above):

| stage | coverage | DRAM% | L2% |
|---|---|---|---|
| ViT | 90.8% | **39.1** | 52.1 |
| prefill | 83.5% | 52.8 | 59.5 |
| decode | 97.4% | 92.4 | 42.6 |

Summing demands for two co-running phases:

| pair | DRAM | L2 | |
|---|---|---|---|
| ViT + decode | **131%** | 95% | DRAM oversubscribed |
| prefill + decode | **145%** | **102%** | both oversubscribed |
| ViT + prefill | 92% | **112%** | L2 oversubscribed |

So ViT and decode are **not** complementary on memory — they collide on DRAM. SM
is genuinely free in both, but no phase here is SM-limited. The ~18% ceiling is
optimistic and the experiment should now be run against a sharper prediction:
**if DRAM is the shared limit, co-running should pin DRAM near 100% and deliver
well under 18%.** That is falsifiable, which the original framing was not.

## Launch-consistency violation — `vit__k_bin_bcast_add__9pct`

Its three launches are **36.5 / 19.8 / 20.4 us — a 65% spread**, far past the 15%
incoherence bar this survey sets. `ncu_targets.py shapes` had flagged that exact
shape *"3x spread at one grid: interleaved problem sizes, target the median"*; the
bare `-c 3` selector took the first three launches and straddled two duration
clusters. The results table above then quotes **launch 0** (36.5 us / 91.2% DRAM)
as if representative.

Both clusters are DRAM-saturated (91.2% vs 88.4/89.4%), so the *finding* stands.
The duration and the stage share are not quotable.

For contrast, decode's grid 3584 shows a 134% raw spread but is **not** a defect:
that is the documented q_proj/down_proj pair, correctly reported as two separate
shapes. Duration clustering distinguishes the two cases; a flat spread check does
not.

## Selection method: the planner was not used

`ncu_targets.py plan` (launch-shape census -> coverage walk -> shortest window
containing >=3 in-phase launches per shape, inside the interquartile band,
mid-phase biased, with predicted grids for verification) emits `../ncu_targets.sh`
with **21** targets. This survey came from `../run_ncu_survey.sh`: **20**
hand-written targets, **13 of which use a bare `-c N`** — the first N launches,
which methodology rule 4 explicitly warns against.

That is harmless for decode (every shape has p10 ~= p50 ~= p90, rho <= 0.12) and
for the prefill GEMMs (p90/p10 < 1.05), and the one shape with real drift
(prefill attention, 11x spread, rho 0.45) *did* get a positioned `-s` curve. It
cost us `k_bin_bcast` above, and the four unprofiled ViT shapes.

`run_ncu_survey.sh` also has **no verification step**, so "Every run verifies the
grids it actually profiled ... Verified correct on all targets" above cannot be
reproduced from the script that produced these files.

## Replay defaults — how to read every number here

No `--clock-control` / `--cache-control` is passed, so ncu defaults apply:

- **clocks are LOCKED to base.** So `--warmup-iters 0` + first-N sampling is not a
  clock-ramp confound — but **ncu durations are not comparable to nsys durations**.
  Time shares must come from nsys; only ratios *within* one report are meaningful.
- **L1 and L2 are FLUSHED before each replay pass.** The 90-97% L2 hit rates are
  therefore **intra-kernel reuse only**; inter-kernel reuse is excluded by
  construction. The L2-wall finding is conservative for that reason.
- **kernel replay** (see the memory save/restore warning in every `.log`): each
  kernel runs several times to collect all passes. Valid per kernel, meaningless
  for anything cross-kernel.

## Tooling defects found (both still live)

`ncu_report.py` cannot reproduce this survey and fails silently:

- its glob is `ncu_*.csv`, but these files are `<phase>__<kernel>__<share>.csv`,
  so it matches nothing and prints **0% coverage for all three stages** without
  an error. That is why this file's tables were assembled by hand.
- its `WANT` table matches **bare metric names**, but `Memory Throughput` appears
  in two sections — SOL (`68.85 %`) and Memory Workload Analysis
  (`318.66 Gbyte/s`). The last row wins, so its `mem%` field holds GB/s labelled
  as a percent. Key on `(section, metric)`, as `ncu_bottleneck.py` does.

Neither defect touched any published number (the affected columns were never
quoted), but both must be fixed before the tool is trusted again.
